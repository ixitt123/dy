## 一手来源与适用性

### 1. GitHub Advisory：GHSA-mwp4-54f8-5fhr / CVE-2026-69192

- 来源：https://github.com/advisories/GHSA-mwp4-54f8-5fhr
- 上游公告：https://github.com/beaugunderson/ip-address/security/advisories/GHSA-mwp4-54f8-5fhr
- 结论：`ip-address <= 10.3.0` 受影响，首个修复版本为 `10.3.1`，严重级别 High，问题类型为 CWE-20/CWE-918。
- 漏洞机制：`Address4` 把带前导零的八位段按十进制解释，而 WHATWG URL、`inet_aton` 和 `getaddrinfo` 按八进制解释；例如库把 `012.0.0.1` 判为公网 `12.0.0.1`，网络栈实际连接 `10.0.0.1`。
- 对本项目适用：当前锁定版本是 `10.2.0`，明确落在受影响范围；项目还处理用户可控 URL，属于 SSRF 信任边界。

### 2. 上游修复提交与 10.3.1 发布

- 修复提交：https://github.com/beaugunderson/ip-address/commit/56368cb3d66c73ba0ee9b6b834fd31b22c2fd71e
- 发布：https://github.com/beaugunderson/ip-address/releases/tag/v10.3.1
- 结论：修复在 `Address4.parse` 和 IPv4 正则两层拒绝 `/^0\d/` 八位段；上游同时加入 `012.0.0.1`、`012.012.012.012`、`010.0.0.1`、尾段前导零及带 CIDR 的回归。
- 对本项目适用：`express-rate-limit@8.5.2` 的 `^10.2.0` 约束兼容 `10.3.1`，可通过根项目 `pnpm.overrides` 统一解析，不必修改上游包或前端。

### 3. WHATWG URL Standard

- 来源：https://url.spec.whatwg.org/
- 结论：IPv4 host 解析仍识别十六进制/八进制数字，并将这种输入标为 `IPv4-non-decimal-part`；这解释了 URL 网络目标与错误的十进制安全分类之间的差异。
- 本机 Node 24.19.0 复现：`new URL('http://012.0.0.1/').hostname === '10.0.0.1'`，`012.012.012.012 -> 10.10.10.10`，`010.0.0.1 -> 8.0.0.1`。
- 对本项目适用：不能把 URL 规范化后的结果当作“原始输入无歧义”的证明；应在 WHATWG URL 丢失原始表示前拒绝含前导零的点分四段主机。

### 4. Node.js `node:net` 官方文档

- 来源：https://nodejs.org/download/release/v24.16.0/docs/api/net.html
- 结论：`net.isIP` / `net.isIPv4` 只接受无前导零的点分十进制 IPv4；`127.000.000.001` 返回无效。
- 对本项目适用：应用层严格字面量判定应与 Node 网络 API 保持一致，不能继续用 `parseInt` 接受 `00`、`01`、`012` 等八位段。

### 5. 同版本相关公告

- GHSA-4xrf-jv44-h6hh / CVE-2026-69198：https://github.com/advisories/GHSA-4xrf-jv44-h6hh ，`10.2.2` 修复 CIDR 后缀抑制特殊地址分类。
- GHSA-22jq-vg5j-6vgg / CVE-2026-54272：https://github.com/advisories/GHSA-22jq-vg5j-6vgg ，`10.2.1` 修复 IPv4-mapped/NAT64 分类。
- 对本项目适用：当前 `10.2.0` 同时受三条 SSRF/信任边界公告影响；升级到 `10.3.1` 一并跨过三个首个修复版本。CIDR 与 IPv4-mapped/NAT64 的应用层扩展仍分别留给 `R2-02.03`、`R2-02.04`，本项不越界重写。

### 6. npm 包元数据

- 来源：https://www.npmjs.com/package/ip-address
- 结论：`10.3.1` 是已发布的零运行时依赖版本；本机 registry 元数据给出的上游仓库为 `https://github.com/beaugunderson/ip-address.git`，`10.3.1` 对应 git head `be7e626c0d49fccb518899f520a3fb64ee189741`。
- 对本项目适用：采用精确 override 能确保所有传递路径统一落到已修复版本，并将锁文件差异限制在供应链切片内。

## 采用方案

1. 在根 `package.json` 的 `pnpm.overrides` 中精确加入 `ip-address: 10.3.1`，重新冻结 `pnpm-lock.yaml`，并用 `pnpm why ip-address` 证明全树只有 `10.3.1`。
2. 在 `server/core/ssrf-guard.mjs` 的 WHATWG URL 解析之前检查原始 authority：若主机是四段纯数字且任一多位八位段以 `0` 开头，立即拒绝。此层用于保证“原始输入、URL 解析、DNS、socket 目标”不会因规范化而产生含义漂移。
3. 新增 `test-ip-address-leading-zero.mjs`：先证明依赖版本至少 `10.3.1` 且上游 `Address4` 拒绝公告样例；再证明应用守卫在 DNS/请求前拒绝歧义输入，并证明普通公网域名仍把已校验 DNS 地址原样固定给连接层。
4. 保留现有“解析全部 DNS 地址、逐个阻断私网、连接时固定已校验地址、每跳重验重定向”结构，不把升级依赖误当作完整 SSRF 防线。
5. `pnpm audit --prod` 当前因用户级 registry 指向 `https://registry.npmmirror.com` 且该站无 audit endpoint 而返回 `ERR_PNPM_AUDIT_ENDPOINT_NOT_EXISTS`。复验时只在当前进程临时设置官方 npm registry 后执行同一条命令，不修改全局 Node/pnpm 或其他项目配置。

## 未采用方案及原因

- 不只升级依赖：本项目 SSRF 守卫没有直接调用 `ip-address`，仅升级不能证明原始 URL、DNS 和实际连接目标一致。
- 不只依赖 WHATWG URL 规范化：它会把 `012.0.0.1` 静默改写为 `10.0.0.1`，虽然当前范围校验能阻断该样例，但审计证据无法区分“明确拒绝歧义输入”和“碰巧规范化后命中私网”。
- 不把前导零按十进制清洗后放行：这会重现公告中的库/网络栈分歧；安全边界必须拒绝歧义而不是猜测用户意图。
- 不升级到刚发布的 `10.4.0`：本项验收下限为 `10.3.1`，选首个修复版本可减少额外行为变化；后续常规依赖升级可单独评估 `10.4.0`。
- 不新增新的 IP Provider/解析库，也不改 MoneyPrinterTurbo：现有 Node URL、DNS 固定连接结构足够承载本项最小修复，扩大依赖或子模块范围会增加兼容风险。
- 不在本项实现 CIDR、IPv4-mapped/NAT64 的完整重构：它们已有独立编号 `R2-02.03`、`R2-02.04`，并行边界要求避免状态所有者重叠。
