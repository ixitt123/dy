## 一手来源与适用性

1. [Node.js v24 File system 文档](https://nodejs.org/download/release/latest-v24.x/docs/api/fs.html)
   - 官方将 `wx` 定义为排他创建：路径已存在时打开失败；`rename` 可把同一文件系统内已完整写好的临时文件发布到目标路径。
   - 适用性：`ui-server.pid` 可继续以 `openSync(..., "wx")` 作为最终抢占点；`ui-server.url` 应先写唯一临时文件、确认仍持有 PID 锁，再重命名发布，避免读到半写内容或由失去所有权的实例覆盖。
2. [Node.js v24 Net 文档](https://nodejs.org/download/release/v24.15.0/docs/api/net.html)
   - `server.listen()` 是异步操作；真正可接受连接时才触发 `listening`，端口冲突通过 `EADDRINUSE` 暴露。
   - 适用性：进程存在与服务 ready 是两个状态。等待方在 owner PID 仍是正确入口时，不能因固定等待窗口内还没有 URL/身份响应就把锁当成陈旧锁删除。
3. [Node.js Child process 文档](https://nodejs.org/api/child_process.html)
   - Windows 上 `detached: true` 可使子进程在父进程退出后继续运行；若要真正独立运行，还需要不继承父进程 stdio 并调用 `unref()`。
   - 适用性：多个并发启动器确实可能同时生成后台子进程；单实例裁决必须由服务端排他锁和所有权校验完成，不能依靠启动器父进程生命周期。
4. [Microsoft `Process.Id` 文档](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.id?view=net-10.0)
   - 官方指出进程退出后系统可复用 PID。
   - 适用性：PID 只用来做锁所有权围栏，不足以单独证明实例身份；必须结合 R2-01.14 已建立的入口命令行核验和实时 HTTP 身份（项目根、入口、commit、实例 ID、URL）。
5. [Microsoft：Using Mutex Objects](https://learn.microsoft.com/en-us/windows/win32/sync/using-mutex-objects)
   - 互斥体用于串行访问共享资源；等待策略必须避免不受控的无限等待。
   - 适用性：本项目需要明确的排他所有者和有界等待，但不采用全局命名互斥体，因为它会引入用户会话/命名空间权限和异常遗留语义；仓库内排他文件更容易与项目根和现有 PID/身份协议绑定。
6. [npm/lockfile 上游仓库](https://github.com/npm/lockfile)
   - 上游实现公开了 `stale`、`wait`、`pollPeriod` 与 `retries` 等锁争用参数。
   - 适用性：说明“锁存在”与“锁陈旧”必须分开处理，等待应有界且可观测；该仓库已归档，本轮不增加依赖，只吸收其状态区分思想。
7. [moxystudio/node-proper-lockfile 上游仓库](https://github.com/moxystudio/node-proper-lockfile)
   - 上游使用原子目录创建并持续更新时间来降低陈旧锁和所有权丢失风险。
   - 适用性：本项目已有更强的 Windows 入口路径和 HTTP 身份证据，因此不引入新库；采用相同的原则：只由仍持锁的 owner 发布/清理状态，等待方不得删除仍活着的合法 owner。
8. [Node.js v24 HTTP 文档](https://nodejs.org/download/release/latest-v24.x/docs/api/http.html)
   - `server.listening` 仅在服务已经绑定后为真。
   - 适用性：URL 只能在监听成功且运行身份 ready 后发布；测试须验证发布内容指向同一个实际监听实例。

## 本仓库诊断

- `ui-server.mjs` 已用 `fs.openSync(pidPath, "wx")` 争抢 PID 文件，这是正确的原子抢占点；R2-01.14 还增加了进程入口和 HTTP 运行身份校验。
- 现有失败路径把“验证完成”和“尚未就绪”折叠为空字符串：等待方最多等待约 3 秒，若活着的正确 owner 尚未发布 URL 或身份端点暂时不可达，就进入 `discardRuntimeState(existingPid)`。
- `discardRuntimeState` 只比较 PID 文件内容，没有再次证明 owner 已死亡或身份已明确错误，因此等待方能够删除仍活着的正确进程的 PID/URL，再取得新锁。原 owner 随后仍会监听并写 URL，形成多个后台进程、所有权丢失或 URL 覆盖。
- `ui-server.url` 在监听成功后使用 `writeFileSync` 直接覆盖。并发失主实例若晚到，仍可能写入 URL；读取方也没有“发布前后所有权”围栏。
- `launch-ui.mjs` 的并发启动会生成多个 detached 子进程，这是允许的瞬时状态；验收要求这些子进程最终收敛为一个受验证的 8787/8080 服务实例，且全部 launcher 日志 runId 保留。
- 当前工作树留下 `ui-server.pid=16616` 和 `ui-server.url=http://127.0.0.1:8787`，实际端口未监听，属于可回收的死亡状态；它不能证明活 owner 竞态已被正确处理。
- 当前不存在 `test-launcher-single-instance.mjs`，因此修复前规定回归将以 `MODULE_NOT_FOUND`、非零退出稳定失败。

## 采用方案

1. 把已有运行实例探测明确分成三类：`verified`（身份完全匹配且 ready）、`pending`（owner PID 仍由正确入口持有，但 URL/身份尚未发布或暂不可达）和 `stale/mismatch`（owner 已死亡、PID/文件无效，或可响应身份明确不匹配）。
2. 对 `pending` 只做有界等待和可操作日志，然后正常结束重复启动请求；绝不删除活着且入口匹配的 owner 锁。后续启动仍可通过身份端点复用该实例。
3. 仅在 owner 已死亡/无效，或可验证证据明确证明状态不属于当前运行实例时，按 PID 所有权围栏清理；清理前再次读取 owner，避免检查与删除之间的 TOCTOU。
4. URL 采用“唯一临时文件 → 再次确认 `runtimeOwnerPid() === process.pid` 且本进程仍持锁 → 原子重命名”的发布流程；失去所有权的实例立即停止，不得写 URL 或清理新 owner 的状态。
5. 新增动态回归覆盖：高并发 Node 启动、活 owner 慢启动不得被抢锁、陈旧死亡锁回收、唯一 PID/唯一 URL/唯一身份、全部 launcher runId 留存、失败候选进程退出，以及根页面刷新与身份端点恢复。
6. 继续复用 R2-01.14 的项目根、入口、完整 commit、PID、instance ID、source mtime 与 URL 绑定；不降低身份安全边界。

## 未采用方案及原因

- 仅依赖 PID 文件：PID 可复用，也无法区分错误入口或另一工作树。
- 固定等待 3 秒后无条件删锁：慢机器、首次加载或杀毒扫描会制造合法慢启动，直接删除活 owner 正是本项竞态根因。
- 端口占用即认定本项目已启动：8787/8080 可能属于无关服务，必须核验项目身份。
- 终止所有 `node.exe` 或端口相关进程：可能杀死其他项目或用户任务，违反精确所有权和不破坏本地环境要求。
- 只给等待时间加大数值：只能缩小概率，不能消除“活 owner 被偷锁”和失主实例覆盖 URL 的状态机缺陷。
- 引入已归档的 `lockfile` 或新增 `proper-lockfile` 依赖：本轮已有排他文件、Windows 入口核验与 HTTP 身份协议；增加依赖会扩大供应链和锁文件变化范围，且不能替代产品级身份判断。
- 使用全局命名 mutex：会增加 Windows 会话、权限、命名冲突与崩溃恢复复杂度，也不天然绑定仓库路径/commit；项目内原子锁加身份围栏更适合当前架构。
- 把 `.data` 证据、Cookie、设置或其他敏感状态写进 Git：证据仍只保存在本机 `.data`，提交只包含研究、源码、测试与权威记录。
