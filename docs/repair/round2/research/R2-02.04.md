# R2-02.04｜IPv4-mapped/NAT64 与 socket 目标再校验：研究记录

- 检索时间：2026-08-05 12:10–12:45、15:25–15:32（Asia/Shanghai）
- 中文关键词：`IPv4-mapped IPv6 SSRF 绕过`、`NAT64 内嵌 IPv4 私网 metadata`、`DNS 解析后 socket 地址二次校验`、`IPv6 link-local fe80 /10`
- English queries: `IPv4-mapped NAT64 SSRF bypass`, `GHSA-22jq-vg5j-6vgg`, `CVE-2026-54272`, `validate resolved IP against socket target DNS rebinding`, `Node.js custom lookup pinned address`, `RFC 4291 IPv4-mapped`, `RFC 6052 64:ff9b::/96`
- 检索优先级：GitHub Reviewed 官方安全公告、上游仓库修复提交/发行版、IETF RFC、Node.js v24 官方文档；未用二手博客决定实现。

## 一手资料与适用性

1. [GitHub Reviewed Advisory GHSA-22jq-vg5j-6vgg / CVE-2026-54272](https://github.com/advisories/GHSA-22jq-vg5j-6vgg)
   - 公告确认 `ip-address >=10.1.1 <=10.2.0` 会按 IPv6 外壳而不是内嵌 IPv4 分类 `::ffff:0:0/96` 与 `64:ff9b::/96`，修复版为 `10.2.1`；当前仓库已锁定更高的 `10.3.1`。
   - 公告列出的可绕过目标包括 `::ffff:127.0.0.1`、`::ffff:a9fe:a9fe`、`64:ff9b::7f00:1`、`64:ff9b::a9fe:a9fe`。它同时强调：地址分类器不是完整 SSRF 防线，必须解析域名、校验解析 IP 与实际 socket 连接目标，并处理 DNS 重绑定和重定向。
   - 直接适用于本项，因为本仓库 `ssrf-guard.mjs` 仍用字符串前缀判断 IPv6，且当前 `safeFetch` 的 socket 前没有独立可复用的最终目标断言。
2. [上游修复提交 `4a1f613`](https://github.com/beaugunderson/ip-address/commit/4a1f613f4c1bec915677dea923c10aaa09361ef9)
   - 上游新增 `embeddedIPv4()`：按地址位识别 IPv4-mapped 与 NAT64 well-known prefix，再把 loopback、link-local、private、CGNAT、multicast、unspecified、broadcast 判断委托给内嵌 IPv4。
   - 修复明确区分文本写法与地址位：`::ffff:127.0.0.1` 和 `::ffff:7f00:1` 必须得到相同结论。
   - 本项采用同一原则，但不直接调用上游包：`ip-address` 在本仓库只是 pnpm 严格布局下的传递依赖；新增直接依赖会扩大 package/lock 变更，且当前 Node 24 已提供足够的 `net.isIP`/`net.BlockList` 原语。
3. [上游发行版 v10.2.1](https://github.com/beaugunderson/ip-address/releases/tag/v10.2.1)
   - 用于确认公告修复已进入正式发行版；仓库现有 `10.3.1` 依赖门禁继续保留。
4. [RFC 4291 §2.5.5.2](https://datatracker.ietf.org/doc/html/rfc4291#section-2.5.5.2)
   - IPv4-mapped IPv6 的格式是 80 位零、16 位 `FFFF`、低 32 位 IPv4，即 `::ffff:0:0/96`。
   - 同一 RFC 规定 IPv6 link-local 是 `fe80::/10`；因此原实现只判断字符串 `fe80` 会漏掉 `fe90::`、`fea0::`、`febf::`。
5. [RFC 6052 §2.1–3.1](https://datatracker.ietf.org/doc/html/rfc6052)
   - IETF 定义 NAT64 Well-Known Prefix 为 `64:ff9b::/96`，低 32 位承载 IPv4；RFC 还要求该前缀不得表示非全局 IPv4，翻译器遇到这种地址应丢弃。
   - 直接支持对 `64:ff9b::/96` 的低 32 位复用现有 IPv4 私网/loopback/link-local/CGNAT拒绝范围，而不是把 NAT64 外壳误当普通公网 IPv6。
6. [RFC 5156 IPv6 Special-Use Address Space](https://datatracker.ietf.org/doc/html/rfc5156)
   - 汇总 `::ffff:0:0/96`、`fe80::/10`、`fc00::/7` 等特殊用途前缀；用于校正原字符串判断的边界。
7. [Node.js v24 `net` 文档](https://nodejs.org/download/release/v24.16.0/docs/api/net.html)
   - `net.isIP()` 提供严格地址族识别；`net.BlockList.addSubnet/check` 支持 IPv4/IPv6 CIDR 位级匹配，可避免手写 IPv6 文本展开器和大小写/压缩写法歧义。
8. [Node.js v24 `http` 文档](https://nodejs.org/download/release/v24.16.0/docs/api/http.html) 与 [DNS 文档](https://nodejs.org/download/release/v24.16.0/docs/api/dns.html)
   - HTTP 客户端允许传入自定义 `lookup`，实际连接由该回调返回的地址/族决定；DNS 还定义可能返回 IPv4-mapped IPv6 的 `V4MAPPED` 行为。
   - 适用于当前 `requestPinned`：必须把经过最终校验的不可变地址/族返回给 socket lookup，不能在域名校验后重新使用系统解析。

## 本地修复前复现

基线：`54a7f8f9fe4aa4784bf9fecb52408133d70f35d1`，Node `v24.19.0`，pnpm `10.33.0`。

1. `node test-socket-target-revalidation.mjs`：退出码 `1`，准确失败为 `MODULE_NOT_FOUND`，说明要求的回归尚不存在。
2. 直接调用 `assertSafeUrl`：以下 5 个目标全部错误地 `ALLOW`：
   - `http://[::ffff:127.0.0.1]/`
   - `http://[::ffff:7f00:1]/`
   - `http://[::ffff:a9fe:a9fe]/`
   - `http://[64:ff9b::7f00:1]/`
   - `http://[64:ff9b::a9fe:a9fe]/`
3. 自定义 DNS 返回 `::ffff:7f00:1` 或 `64:ff9b::a9fe:a9fe` 时，`requestImpl` 各被调用 `1` 次；原生 `fe80::1` 会在请求前阻断。
4. Node URL 会把点分十进制 `::ffff:127.0.0.1` 规范化为十六进制 `::ffff:7f00:1`，所以只检查 `::ffff:` 后是否包含 `.` 必然可绕过。
5. Node 24 `net.BlockList` 本地探针证明，同一 CIDR 规则可同时识别 mapped/NAT64 的点分与十六进制形式，并允许内嵌公网 IPv4（如 `93.184.216.34`）。

## 根因

- `isPrivateIPv6` 依赖字符串前缀；IPv4-mapped 只有保留点分写法时才下沉 IPv4 判断，但 WHATWG URL 会先规范化为纯十六进制。
- 完全没有识别 `64:ff9b::/96` 的内嵌 IPv4。
- link-local 只写成 `startsWith("fe80")`，没有覆盖 RFC 4291 的完整 `fe80::/10`。
- DNS 返回地址虽逐个检查，但缺少独立、可测试的 socket 目标断言和 address/family 一致性校验；最终连接层应再次验证并只持有不可变的已验证副本。

## 采用方案

1. 保留现有 IPv4 拒绝策略并为每个 CIDR记录精确 prefix；补充 multicast/reserved/broadcast `224.0.0.0/4`，避免这些特殊目标经 mapped/NAT64 进入 socket。
2. 使用 Node 内置 `net.BlockList` 构建位级 IPv6 规则：原生 `::/128`、`::1/128`、`fe80::/10`、`fc00::/7`、`ff00::/8`；并把每个被拒 IPv4 CIDR映射为 `::ffff:0:0/96 + IPv4 prefix` 与 `64:ff9b::/96 + IPv4 prefix`。
3. 新增统一地址/族校验：严格 `net.isIP`、拒绝声明 family 与实际 family 不一致、拒绝特殊地址，返回冻结的新对象。
4. DNS 全量结果继续逐个校验；`safeFetch` 选择地址后在调用 `requestImpl`/真实 HTTP 客户端前第二次执行 socket 目标校验；`requestPinned` 再持有最终冻结副本并由自定义 lookup 返回，保持 DNS pinning。
5. 新回归覆盖 mapped 的点分/十六进制、NAT64、完整 link-local、metadata、family mismatch、请求不得发生，以及内嵌公网 IPv4 正常通过；原 `test-ssrf-guard.mjs` 必须继续通过。
6. 把新回归加入 `check:gate`，防止后续只跑旧 SSRF 测试时回退。

## 未采用方案

- 只升级 `ip-address`：仓库已是 `10.3.1`，但业务 guard 并未调用该传递依赖，不能修复本地字符串逻辑或 socket 二次校验。
- 继续用字符串 `startsWith`/正则展开 IPv6：无法可靠处理压缩、大小写、点分与十六进制等价写法，也容易再次写错 `/10` 边界。
- 新增 `ip-address` 直接依赖：会扩大 package/lock 和供应链范围；Node 24 内置位级 CIDR足够，当前 assignment 也不授权修改锁文件。
- 阻断整个 `::ffff:0:0/96` 或 `64:ff9b::/96`：会把内嵌公网 IPv4 一并误杀；采用按低 32 位复用现有 IPv4 策略。
- 只校验 DNS 返回值、不固定实际连接地址：仍留下 DNS 重绑定窗口；继续使用自定义 lookup pinning 并增加 socket 前再校验。
- 猜测或阻断所有 Network-Specific NAT64 前缀：部署前缀不是从地址本身可靠推断；本项按 RFC 6052 与公告处理 Well-Known Prefix，其他组织前缀必须由部署配置单独声明。
- 修改 MoneyPrinterTurbo 或子模块指针：与本项无关且明确禁止。
