## 一手来源、结论与适用性

### 1. 上游安全公告 GHSA-v2hh-gcrm-f6hx / CVE-2026-16221

- 来源：[fast-uri 官方安全公告](https://github.com/fastify/fast-uri/security/advisories/GHSA-v2hh-gcrm-f6hx)。
- 公告范围：`>=2.3.1 <=2.4.2`、`>=3.0.0 <=3.1.3`、`>=4.0.0 <=4.1.0` 受影响；首个修复版分别为 `2.4.3`、`3.1.4`、`4.1.1`。公告评级 High，CVSS 7.5，CWE-436，且没有安全替代配置，必须升级。
- 漏洞机制：字面量反斜杠 U+005C 位于 authority 时，旧版 `fast-uri` 与浏览器/Node WHATWG URL 对主机边界的解释不同。例如 `http://evil.com\@allowed.com` 可能被策略层误判为 `allowed.com`，而实际网络使用方连接 `evil.com`。
- 对本项目适用：`fast-uri` 经 Ajv 间接进入生产依赖；项目同时存在用户可控 URL、重定向与 SSRF 信任边界，因此既要锁定安全版本，也要验证策略解析主机、DNS 结果和实际 socket 目标一致。

### 2. 上游修复提交与回归

- 来源：[上游补丁 `2d50fba`](https://github.com/fastify/fast-uri/commit/2d50fba)、[v3.1.3...v3.1.4 对比](https://github.com/fastify/fast-uri/compare/v3.1.3...v3.1.4)。
- 上游做法：在 `parseWithStatus` 中抽取 authority 前缀；authority 含字面量 `\` 时设置准确错误 `URI authority must not contain a literal backslash.`，不把它静默改写成 `/`。补丁同时覆盖 HTTP、HTTPS、WS/WSS、无 scheme authority、反斜杠加 `%40`，并确认 `%5C` 仍作为编码数据处理。
- 对本项目适用：动态测试应直接调用实际安装的 `fast-uri`，验证公告样例确实被拒绝；应用层仍以同一个 WHATWG `URL` 对象完成校验和请求，避免“安全库解析一次、网络库再按另一规则解释”的双解析器分歧。

### 3. 后续公告 GHSA-7p8r-x3mc-p8w7 / CVE-2026-18446

- 来源：[GitHub Advisory Database](https://github.com/advisories/GHSA-7p8r-x3mc-p8w7)、[fast-uri 官方安全公告](https://github.com/fastify/fast-uri/security/advisories/GHSA-7p8r-x3mc-p8w7)、[上游修复提交 `f3c6c90`](https://github.com/fastify/fast-uri/commit/f3c6c90)、[v3.1.5 发布](https://github.com/fastify/fast-uri/releases/tag/v3.1.5)。
- 公告范围：`3.0.0 <= version < 3.1.5` 受影响，3.x 首个修复版是 `3.1.5`；评级 High，CVSS 7.5，CWE-436，且无替代配置。公告 2026-07-31 发布，2026-08-03 进入 GitHub Advisory Database。
- 漏洞机制：v3.1.4 虽拒绝 authority **内部** 的字面量反斜杠，但仍只把精确 `//` 识别为 authority introducer。WHATWG URL 会为特殊 scheme 把 `\\`、`/\`、`\/` 视作 `/`，并在解析前删除 TAB/LF/CR，因此策略解析器可能把输入当路径，而实际网络使用方把它解析为攻击者主机。
- 上游修复：检查 scheme 后的分隔符区域，拒绝畸形反斜杠或空白拆分的 authority introducer；`resolve()` 在无法通过返回值表达错误时改为抛错。上游加入 23 个覆盖 parse、normalize、equal、resolve 与误报边界的回归。
- 本机真实证据：第 1 次完整复验中，`pnpm.cmd audit --prod --registry=https://registry.npmjs.org` 对 `fast-uri@3.1.4` 返回 High、非零退出，证据位于 `.data/repair-evidence/R2-02.01/20260805-215852/attempt-1/`。因此 3.1.4 不能再被声明为“安全版本”。

### 4. 上游 v3.1.4/v3.1.5 安全发布与 npm 元数据

- 来源：[fast-uri v3.1.4 发布](https://github.com/fastify/fast-uri/releases/tag/v3.1.4)、[npm 版本页](https://www.npmjs.com/package/fast-uri?activeTab=versions)。
- 结论：v3.1.4 只修复较早的 GHSA-v2hh-gcrm-f6hx；v3.1.5 才同时覆盖后续 GHSA-7p8r-x3mc-p8w7。npm 审计数据明确把 `<3.1.5` 标为受影响。
- 本地适用：根 `pnpm.overrides.fast-uri` 与锁文件必须从 `3.1.4` 精确升级为 `3.1.5`，然后用 `pnpm why` 和官方 registry 审计证明依赖树没有残留旧版及对应公告。

### 5. Node.js 24 WHATWG URL 与 HTTP 请求契约

- 来源：[Node.js URL 官方文档](https://nodejs.org/api/url.html#the-whatwg-url-api)、[Node.js 24 HTTP 官方文档](https://nodejs.org/docs/latest-v24.x/api/http.html#httprequesturl-options-callback)。
- 结论：Node 的现代 `URL` API 实现浏览器使用的 WHATWG URL Standard；`http.request` 接受 WHATWG `URL`。本项目当前 `resolveSafeUrl` 返回同一个 `URL` 实例给请求层，并通过自定义 `lookup` 把已经逐个校验的 DNS 地址固定到 socket。
- 对本项目适用：回归不能只静态检查版本或代码文本，必须动态证明解析后的 `hostname`、DNS 输入、`requestImpl` 看到的 URL 主机与固定地址完全一致，并证明恶意重定向在第二次请求前被拒绝。

### 6. 相关的 percent-encoded authority 公告

- 来源：[GHSA-v39h-62p7-jpjc / CVE-2026-6322](https://github.com/fastify/fast-uri/security/advisories/GHSA-v39h-62p7-jpjc)。
- 结论：旧版 `fast-uri <=3.1.1` 还存在 `%40`、`%3A` 等编码分隔符造成的策略/使用方解释分歧，3.x 首个修复版为 3.1.2。
- 对本项目适用：3.1.5 已跨过该修复版本；新增测试保留编码 authority 样例，防止将来依赖回退时只覆盖反斜杠而漏掉同类解析器分歧。

## 采用方案

1. 把 `pnpm.overrides.fast-uri` 从 `3.1.4` 精确升级为 `3.1.5`，用冻结锁文件安装并确认整棵依赖树只有该安全版本；不升级 Ajv、不跨到 fast-uri 4.x。
2. 新增 `test-fast-uri-host-confusion.mjs`，从 pnpm 实际解析的依赖位置加载 `fast-uri`，读取真实 `package.json` 并验证版本与锁文件均为 3.1.5。
3. 动态执行两批上游矩阵：authority 内字面量反斜杠，以及 `\\`、`/\`、`\/`、TAB/LF/CR 拆分的畸形 authority introducer；确认 parse/resolve 明确拒绝，并用 Node WHATWG URL 记录真实网络主机。
4. 动态验证本项目 `safeFetch`：初始 URL 与每一跳重定向均重新解析和 DNS 校验；私网/混合 DNS 在 `requestImpl` 前被拒绝；公网 DNS 地址原样固定给连接层；连接层收到的 URL 主机、DNS 查询主机和策略主机一致。
5. 把新增回归接入 `check:gate`，使未来依赖回退、锁文件漂移或 SSRF 请求链退化均阻断正式门禁。

## 未采用方案及原因

- 不降级到 3.1.3 做“真实复现”：会主动把已修复高危依赖写回 `node_modules` 或锁文件，污染其他测试且扩大暴露面。修复前失败应来自本仓库缺少强制动态回归，而非制造一个脆弱运行环境。
- 不升级到 4.1.2：当前 Ajv 8.20.0 已与 3.x 修复线兼容，3.1.5 是官方同时修复两类反斜杠混淆的最小安全版本；跨主版本会扩大兼容与回滚范围。
- 不复制上游解析器或写静态正则模拟漏洞：模拟器不能证明实际安装版本和真实调用链安全，容易产生假通过。
- 不只运行 `pnpm audit` 或只断言锁文件文本：审计元数据不能证明重定向、DNS 与实际连接地址的运行时一致性。
- 不改写 MoneyPrinterTurbo、全局 Node/pnpm、用户设置、SQLite、密钥或本地素材：它们不属于本项依赖与 SSRF 信任边界。

## 修改边界与回滚

- 业务 SSRF 行为无需改动；供应链需升级到 3.1.5，并新增安全动态回归接入正式门禁。若动态回归发现现有 `ssrf-guard` 真实缺陷，才在已授权的 `server/core/ssrf-guard.mjs` 内做最小修复并单独记录失败原因。
- 回滚只反向撤销本项提交，不删除 `.data` 证据，不改协作历史，不 rebase、不强推，并保持 `integrations/moneyprinterturbo` gitlink 为 `d994b15fc8f4b8a9eeb7d43cc8aed4a2a0e2c3f2`。
