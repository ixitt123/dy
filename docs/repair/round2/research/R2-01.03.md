## 一手来源与适用性

### 1. WHATWG HTML Living Standard：隐藏元素

- 来源：[HTML Standard — Rendering](https://html.spec.whatwg.org/multipage/rendering.html)。
- 要点：`hidden` 通常表示元素不参与渲染；仅移到屏幕外不等于未渲染。
- 适用性：无有效 BGM 时，BGM 播放器或操作按钮必须从渲染树中移除或正确隐藏，不能只靠视觉位移或留下可操作控件。

### 2. W3C/WAI：动态控件的名称、角色和状态

- 来源：[WCAG 2.2 Understanding 4.1.2 — Name, Role, Value](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value)。
- 要点：脚本生成或动态变化的控件必须向用户代理提供正确、可更新的名称、角色、状态和值。
- 适用性：BGM 按钮是否存在、三件套/四件套可见标签和中央发送按钮文字必须同时反映当前任务的真实关系状态；不能出现“标签说三件套但仍有 BGM 按钮”的互相矛盾状态。

### 3. Redux 官方文档：单一状态源

- 来源：[Redux — Getting Started](https://redux.js.org/introduction/getting-started/)。
- 要点：数据随时间变化且多个界面消费者依赖它时，需要单一事实来源。
- 适用性：历史行标签、文件按钮、中央发送按钮和状态提示应复用同一个“当前任务是否拥有有效 BGM 关系”的选择器结果，避免各处独立猜测。

### 4. JSON:API 1.1：关系与唯一 ID

- 来源：[JSON:API — Latest Specification](https://jsonapi.org/format/index.html)。
- 要点：资源以唯一 `type`/`id` 标识；关系应使用明确的 relationship linkage，复合资源必须能通过关系链回到主资源。
- 适用性：本项目不是 JSON:API 实现，但其关系建模原则直接适用于 TTS/BGM：只有精确 `parent_tts_job_id` / `source_tts_job_id` 且通过本地关系校验的 BGM 才能驱动四件套 UI。

## 本地调用链与修改前证据

- 权威关系入口：`indexTtsBgmJobs()` 把合法子任务按父任务 ID 建立索引，`linkedTtsBgmJob()` 是历史行和中央交接 UI 的共同读取入口。
- 历史行：`renderTtsJobsEnhanced()` 根据同一个 `linkedBgm` 同时决定 BGM 按钮、文件清单、三件套/四件套标签。
- 中央交接：`ttsHandoffBundleLabel()` 和 `syncTtsCentralHandoffBundle()` 根据关联 BGM 的可用音频路径决定发送按钮及状态文案。
- 修改前回归 `test-tts-bundle-labels.mjs` 固定读取另一台机器的任务 `92/93`，在当前 B 数据库中于 30 秒后超时，未到达任何业务断言；不能作为可复现验收。
- 失败证据：`.data/repair-evidence/R2-01.03/20260805-184123/pre-fix/01-bundle-labels.log`。
- 准确失败点：`test-tts-bundle-labels.mjs:39` 等待 `[data-tts-job-id="92"]` 超时。
- 根因分类：跨机器本地 SQLite fixture 耦合；不是当前业务源码已经证明失败。必须先把回归改为自包含安全 fixture，再判断在 `R2-01.02` 关系修复后的真实产品状态。

## 采用方案

1. 使用仓库内安全 WAV，通过正常本地 API 创建一条显式无 BGM 的旁白，以及一条显式需要 BGM 且具备已确认精确父子关系的旁白/BGM。
2. 在同一 fresh headless Chrome 会话中验证历史行标签、BGM 按钮、文件清单、中央发送按钮和状态文案；刷新后重复验证。
3. SQLite、API 和 DOM 三层都核对精确任务 ID；测试默认通过正常删除 API 清理 fixture。
4. 若自包含回归显示业务源码已满足验收，仅修复失效的测试基建，不为了制造源码差异改写正确逻辑。

## 未采用方案及原因

- 继续使用任务 `92/93`：数据只存在于原机器，无法在 B 主机或 CI 复验。
- 按文案、时间或相邻顺序寻找 BGM：会重新引入 `R2-01.02` 已消除的错误关联。
- 只检查字符串或 CSS 源码：不能证明真实 API、DOM、刷新和按钮行为。
- 用固定假 DOM/mock 数据：绕过实际页面、关系索引和事件绑定。
- 无 BGM 时只禁用按钮：验收要求“不显示按钮”，且无可执行目标的控件会制造状态歧义。
- 删除历史用户记录或迁移 SQLite：扩大数据风险；本项可用自包含 fixture 完成验证。

## 研究结论

本项应把“有效 BGM 关系”作为唯一 UI 状态源，并以精确任务 ID、可用音频资源及已确认关系共同判定。当前首先需要修复跨机器硬编码回归；业务源码是否仍需修改，必须由新的自包含真实浏览器回归决定。
