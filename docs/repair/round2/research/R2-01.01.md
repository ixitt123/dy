# R2-01.01 修改前研究：TTS 自动预览与浏览器自动播放策略

- 检索关键词：`HTMLMediaElement play promise autoplay policy user gesture`、`Chrome autoplay muted play NotAllowedError`、`WHATWG media play pending promises`、`WebKit autoplay audio user gesture`、`MDN autoplay failure controls`、`Chromium HTMLMediaElement autoplay policy`。

## 一手来源、适用性与结论

1. [WHATWG HTML：媒体元素](https://html.spec.whatwg.org/multipage/media.html)
   - `play()` 通过 pending play promises 表达异步成功或失败；只有元素进入可播放状态后 Promise 才会兑现，`currentTime` 在潜在播放状态下才会单调前进。
   - 适用性：本项不能用“设置了 `src`、调用了 `load()` 或播放器可见”代替播放成功，必须等待 `play()` 结果并用真实 `currentTime > 0.15` 验证。
2. [WHATWG HTML：用户激活](https://html.spec.whatwg.org/multipage/interaction.html#tracking-user-activation)
   - 可信鼠标/触摸/键盘输入建立用户激活；浏览器可把受限能力与该状态绑定。
   - 适用性：生成按钮的真实点击是产品侧的用户意图，但 TTS 完成发生在长异步链之后，不能假定所有浏览器仍保留瞬时激活；代码必须处理被拒绝的 `play()`。
3. [Chrome 官方自动播放策略](https://developer.chrome.com/blog/autoplay/)
   - 静音自动播放通常允许；有声自动播放取决于用户对站点的交互、媒体参与度或策略。官方要求检查 `play()` 返回的 Promise，并在拒绝时显示可手动播放的控件。
   - 适用性：本地 Chrome/Edge 页面应主动尝试播放；不能通过测试参数关闭自动播放策略，也不能假定 fresh profile 一定允许有声播放。
4. [Chrome 官方：`HTMLMediaElement.play()` returns a promise](https://developer.chrome.com/blog/play-returns-promise/)
   - Promise 兑现表示实际开始播放；浏览器可延迟开始，固定延时或仅监听资源加载会产生误判。
   - 适用性：实现应等待 Promise，并让回归基于 `currentTime` 前进，而不是只检查 `paused`、`readyState` 或固定 sleep。
5. [Chromium：Autoplay of HTMLMediaElements](https://chromium.googlesource.com/chromium/src/+/3ee9f7924f/docs/media/autoplay.md)
   - `autoplay` 属性与脚本 `play()` 都受 AutoplayPolicy 裁决；拒绝时元素保持暂停。
   - 适用性：仅给 `<audio>` 增加 `autoplay` 不能可靠修复，也不能提供准确失败状态；显式 `play()` 加 Promise 处理更可验证。
6. [MDN：HTMLMediaElement.play()](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/play)
   - `play()` 返回 Promise；策略阻止时通常以 `NotAllowedError` 拒绝，媒体不支持时可为 `NotSupportedError`。页面不得在 Promise 结果未知时假定已经播放。
   - 适用性：拒绝必须被捕获，避免未处理 Promise；自动播放被策略阻止时保留原生 controls，并显示“点击播放器开始试听”的可操作提示。
7. [MDN：Autoplay guide（上游内容）](https://github.com/mdn/content/blob/main/files/en-us/web/media/guides/autoplay/index.md)
   - 自动播放失败应提供手动 controls；静音或音量为零通常更容易获准，但策略仍可能因浏览器/用户设置不同而变化。
   - 适用性：自动化可以在真实安全 fixture 上使用静音验证播放状态，但产品代码不得永久静音用户旁白或伪装有声自动播放成功。
8. [WebKit：macOS 自动播放策略](https://webkit.org/blog/7734/auto-play-policy-changes-for-macos/)
   - WebKit 建议默认认为音视频可能需要用户手势，检查 `play()` Promise，并在拒绝时保留可操作 UI；连续媒体应复用同一个媒体元素。
   - 适用性：继续复用现有 `#ttsAudio`，切换任务时更新其 source，不创建隐形 Audio 实例；这样手动回退和当前任务绑定不会分叉。

## 本仓库诊断

- `waitForTtsJob()` 在任务完成后调用 `showTtsPreview(displayJob, { reveal: true })`；后者只设置 `src`、调用 `load()`、渲染信息并滚动到播放器，从未调用 `ttsAudio.play()`。
- 因此“生成完成后播放器可见”与“开始播放”被错误地当成同一状态，根因位于前端预览状态机，不在 TTS Provider、SQLite、音频文件生成或 SSRF 路由。
- 现有 `test-tts-auto-preview.mjs` 在检查 `currentTime` 前主动向 `<audio>` 控件派发鼠标点击；该点击会替产品补上缺失的播放动作，所以测试能证明文件可手动播放，却不能证明自动预览。
- 测试使用 fresh headless Chrome profile 且没有 `--autoplay-policy=no-user-gesture-required`，适合作为真实策略环境；测试必须禁止媒体控件点击，并记录 `play`/`playing`/错误状态。
- B 主机隔离仓库没有 TTS API Key；直接调用供应商会进入人工配置提示。真实供应商验收属于独立的 `R2-01.10`，本项完成判定明确要求“安全 fixture”，因此回归通过正常 `/api/tts/import-generated` 路径导入仓库内可解码 WAV，再走同一 `waitForTtsJob()` 完成状态机；不读取、伪造或要求用户补 API Key。

## 采用方案

1. 在现有 `#ttsAudio` 上建立单一自动预览函数：确认 job/source 仍属于当前活动任务后调用 `play()`，等待 Promise，返回结构化成功或拒绝结果。
2. 任务完成并加载 source 后主动尝试一次播放；不通过固定延时声称成功，不创建第二个 Audio 对象，不修改后端或 Provider。
3. 成功时以 Promise 兑现及后续 `currentTime > 0.15` 为验收；失败时捕获 `NotAllowedError`/其他媒体错误，保持原生 controls 可见并给出明确手动播放提示，不伪造成功。
4. 更新真实浏览器回归：通过正常导入 API 建立可解码、可哈希的安全旁白任务；移除对音频控件的鼠标点击；直接等待非静音自动播放推进，并保存自动播放状态、任务 ID、source、`currentTime`、`paused`。随后切换到另一任务再切回，并刷新页面重新加载同一已完成任务，验证 source/任务不串且仍可播放。
5. 所有浏览器进程使用现有 headless CDP 与独立临时 profile，结束时精确回收；不打开可见窗口，不修改或上传本地设置、SQLite、音频与 `.data` 证据。

## 未采用方案及原因

- 只增加 `<audio autoplay>`：仍受同一策略约束，且无法可靠处理 Promise 拒绝与 UI 状态。
- 给测试加入 `--autoplay-policy=no-user-gesture-required`：会绕过真实浏览器策略，产生虚假通过。
- 永久设置 `muted=true` 或 `volume=0`：虽可提高自动播放成功率，但用户听不到旁白，不满足产品缺陷目标；静音只可用于无声自动化取证。
- 自动重试 `play()` 直到成功：策略拒绝不会因轮询自行消失，会制造噪声和资源占用；正确回退是可见 controls 与可操作提示。
- 新建隐藏 `Audio()` 播放：会与页面播放器形成两个状态所有者，切任务/刷新更容易串音，也违反 WebKit 建议的单元素复用。
- 修改 TTS Provider、SQLite、后端音频生成或安全路由：真实音频已能加载并手动播放，证据指向前端未调用播放，不应扩大修改面。
- 把测试中的媒体控件点击继续算作“自动预览”：该动作直接掩盖本项根因，必须移除。
