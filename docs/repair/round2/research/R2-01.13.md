# R2-01.13｜launcher 日志可靠性、并发追加与轮转：研究记录

- 检索时间：2026-08-05 11:35–11:55（Asia/Shanghai）
- 中文关键词：Windows Script Host 日志并发追加、FileSystemObject ForAppending、Windows 文件锁、日志轮转恢复、并发写不丢
- English queries: `Windows concurrent append file locking`, `FileSystemObject OpenTextFile ForAppending`, `Node.js concurrent file modifications appendFile`, `Node.js mkdir lock directory`, `Windows MoveFile rotation recovery`
- 检索范围：优先微软与 Node.js 官方文档；未采用社区代码作为行为依据。

## 一手资料及适用性

1. [Microsoft OpenTextFile method](https://learn.microsoft.com/en-us/office/vba/language/reference/user-interface-help/opentextfile-method)
   - 官方确认 `ForAppending=8` 只保证从文件末尾追加，并说明 `TextStream.Close` 完成关闭；文档没有承诺多个进程同时打开和追加时自动串行化。
   - 适用于当前 `start-ui-hidden.vbs` 的实际 `FileSystemObject.OpenTextFile(..., 8, True)` 调用。
2. [Microsoft Locking and Unlocking Byte Ranges in Files](https://learn.microsoft.com/en-us/windows/win32/fileio/locking-and-unlocking-byte-ranges-in-files)
   - 官方明确指出多个应用可以同时写文件，但必须避免互相覆盖；临时独占锁用于协调并发写入。
   - 适用于确定“直接并发追加不够”；VBS 无法直接调用 `LockFileEx`，因此采用两个运行时都能原子创建的锁目录实现等价的跨进程互斥。
3. [Microsoft Appending One File to Another File](https://learn.microsoft.com/en-us/windows/win32/fileio/appending-one-file-to-another-file)
   - 官方示例在移动文件指针并写入前显式锁定，写完立即解锁，以保证追加数据完整。
   - 适用于要求“并发写不丢”，支持把“轮转检查、轮转、单条追加”放在同一个临界区。
4. [Microsoft MoveFile method](https://learn.microsoft.com/en-us/office/vba/language/reference/user-interface-help/movefile-method)
   - 目标文件已存在时移动会报错；多个移动发生错误时不会自动回滚。
   - 适用于 VBS 轮转：必须在互斥锁内从最旧备份倒序处理，先删除确定目标，再逐个移动，并在任何错误后保证释放锁。
5. [Node.js v24 File system documentation](https://nodejs.org/docs/latest-v24.x/api/fs.html)
   - Node 官方明确说明文件系统 Promise 操作彼此不同步、不是线程安全的；并发修改同一文件可能造成数据损坏。文档同时提供 `appendFileSync`、`mkdirSync`、`renameSync`、`statSync` 等同步原语。
   - 适用于当前 Node 24 基线和 `launch-ui.mjs`；不能假设多个 `appendFile` 自动安全，必须显式串行化。
6. [Node.js v24 Process documentation](https://nodejs.org/docs/latest-v24.x/api/process.html)
   - `process.pid` 和 `process.cwd()`/项目路径可作为结构化日志中的真实进程与项目字段。
   - 适用于 Node 启动、复用和错误事件的 PID、项目字段。

## 当前实现与根因

- VBS 只有 `Now() + message` 的非结构化文本；没有事件、项目、PID、URL字段。
- `LogLine` 使用 `On Error Resume Next` 包住创建目录、打开、写入和关闭，任何共享冲突、磁盘错误或轮转错误都会被静默吞掉。
- 没有文件大小上限或备份，长期运行会无限增长。
- `launch-ui.mjs` 不写 launcher 日志，因此无法区分复用现有服务、启动新服务和 Node 侧错误，也无法记录真实子进程 PID 与 URL。
- VBS 与多个并发启动器可能同时打开同一文件，当前没有跨进程互斥；微软与 Node 文档均不支持把这种方式视为可靠并发追加。

## 采用方案

1. 使用 `.data/launcher-log.lock` 锁目录作为 VBS 与 Node 共用的跨进程互斥：创建成功即持锁，已存在则有限重试；超过陈旧阈值可清理后恢复。
2. 在同一个锁内完成：检查大小、倒序轮转、追加完整单行、关闭文件；无论成功失败都释放锁。
3. 默认单文件上限 256 KiB、保留 3 个备份；测试可通过环境变量降低阈值，但非法值回退安全默认值。
4. 使用逐行 JSON 结构，固定包含 `timestamp`、`event`、`project`、`pid`、`url`、`runId` 和 `message`。没有可用服务 PID/URL的预检阶段使用 `0`/`null`，字段仍明确存在，不伪造不存在的值。
5. VBS 创建或继承单次 `runId` 并传给 Node；Node 使用真实 `process.pid`，启动新服务时记录真实子进程 PID，复用时记录实际 URL。
6. Node 启动新服务后只做有界等待，读取本次写入/更新的 `ui-server.url` 后记录；不在本项判断陈旧项目身份，该责任保留给 R2-01.14。
7. 写日志失败不得改变启动器原有成功/失败语义；控制台输出明确警告，并保留启动或原始错误。日志锁必须有上限，不能造成永久启动阻塞。

## 未采用方案

- 继续直接 `OpenTextFile(...ForAppending)` 或 `appendFile`：官方没有并发安全保证，Node 还明确警告并发修改可能损坏。
- 只让 VBS 写日志：无法获得 Node 复用、新服务子进程 PID和真实 URL。
- 只让 Node 写日志：缺 Node 的最早失败路径无法记录。
- 直接调用 Win32 `LockFileEx`：VBS 需要额外原生/COM桥接，超出本项范围并增加部署依赖；共享锁目录可由现有两个运行时实现和复验。
- 每次复制后清空活动日志：复制与清空之间会丢并发写；改为锁内倒序移动。
- 无限等待锁或无限保留日志：会把日志故障放大为启动故障，并造成磁盘持续增长。
- 修改 `ui-server.mjs` 提供服务 PID/实例身份：该文件不在允许范围；项目/陈旧 URL 的权威校验属于 R2-01.14，如确需修改必须交 B 重新划界。

## 验收设计

- 修复前回归必须证明：缺少结构化字段、并发事件丢失或交错、日志无限增长且无可恢复轮转。
- 修复后真实隔离夹具覆盖：VBS 错误、Node 错误、新服务启动、现有 URL 复用、并发多进程写、达到大小上限后的多代轮转、陈旧锁恢复。
- 汇总活动日志和所有备份后，每个唯一 `runId` 必须完整出现；每行必须能被 JSON 解析且字段齐全。
- 活动日志大小受限，备份数不超过配置；轮转后继续写入成功。
- 随后执行本项测试、完整门禁、第二轮总表检查和 `git diff --check`。
