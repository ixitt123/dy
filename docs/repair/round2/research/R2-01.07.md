## 一手来源与适用性

### 1. WHATWG HTML Living Standard：媒体时间与精确 seek

- 来源：[HTML Standard — Media elements](https://html.spec.whatwg.org/multipage/media.html)。
- 要点：设置 `currentTime` 会更新正式播放位置并启动 seek；`seeking` 表示定位仍在进行，`seeked` 表示定位完成；需要精确位置时应设置 `currentTime`，不能用可能降低精度的近似 seek 代替。
- 适用性：主预览拖动必须把同一个目标秒数写入旁白与 BGM；验证不能只看滑杆文本，应同时记录主时钟、旁白 `currentTime`、BGM `currentTime`、`seeking/seeked` 状态。

### 2. MDN：`currentTime`、`duration` 与可 seek 范围

- 来源：[HTMLMediaElement.currentTime](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/currentTime)、[Audio and video delivery](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Audio_and_video_delivery)。
- 要点：`currentTime` 单位为秒，设置后媒体从目标时间开始或继续；时长来自 `duration`，可用 `seekable` 判断可定位范围。
- 适用性：BGM 比旁白长时目标应为主预览时间对 BGM 时长取模；每次写入前须确认媒体至少已取得 metadata，测试应允许浏览器完成异步 seek 后再判定误差。

### 3. W3C：不要用低频 `timeupdate` 驱动同步

- 来源：[Requirements for Media Timed Events](https://www.w3.org/TR/media-timed-events/)。
- 要点：`timeupdate` 的约 250ms 更新粒度和不同浏览器的时序差异不适合精确同步；同步渲染可轮询主媒体 `currentTime`，并使用 `requestAnimationFrame()` 获得更平滑时钟。
- 适用性：保留旁白作为主媒体时钟、`requestAnimationFrame()` 驱动画布的架构；不增加 `timeupdate` 驱动的第二时钟。只在开始、拖动提交、刷新恢复和明显漂移时校准 BGM。

### 4. Chrome 官方：播放 Promise 与用户手势

- 来源：[Chrome for Developers — Autoplay policy](https://developer.chrome.com/blog/autoplay/)。
- 要点：有声 `play()` 可能因缺少用户手势而拒绝，界面状态不能假设播放已成功，应处理 Promise；真实验证不应关闭自动播放策略。
- 适用性：回归必须使用 fresh Chrome 和物理点击主播放按钮；分别确认旁白、BGM 的 `paused/currentTime`，不能仅凭按钮文字宣称播放。

### 5. Web Platform Tests 与 WHATWG 上游讨论

- 来源：[web-platform-tests/wpt](https://github.com/web-platform-tests/wpt)、[WHATWG HTML issue #609](https://github.com/whatwg/html/issues/609)。
- 要点：WPT 是浏览器共享的 Web 平台测试基线；上游讨论明确指出浮点时间和媒体容器时间尺度会使逐帧定位存在舍入，验收应使用合理误差而非不稳定的严格单点比较。
- 适用性：本项按“主/BGM 时间差在明确阈值内”验收，保存原始小数和 seek 完成状态；不以 `>0.5` 一类与 fixture 时长偶合的单边断言代替同步误差。

## 本地调用链与修改前证据

- `previewDuration()` 以已解码旁白时长为主时长；`seekValueToTime()` 把 0–1000 滑杆映射到主时长。
- `anchorPreviewClock()` 保存唯一主预览时钟；`previewClockTime()` 优先旁白 `currentTime`，seek 锁定期间使用锚定时钟。
- `syncPreviewMediaTime()` 同时写旁白、BGM 和背景视频时间；BGM 使用 `targetTime % bgm.duration`。
- `beginPreviewSeek()` 在拖动开始时记住播放状态并暂停所有媒体；`finishPreviewSeek()` 再次提交目标并按原状态恢复播放。
- `previewTick()` 使用 `requestAnimationFrame()` 更新画布，但播放过程中没有周期性校正 BGM 漂移；开始与 seek 提交是当前主要同步点。
- 修改前 `test-kinetic-bgm-player-browser.mjs` 使用真实安全 WAV 和 headless Chrome，主预览播放后 BGM 能推进，但把滑杆设为 500 并派发 `input/change` 后在第 97 行失败：`拖动主预览时间后可见 BGM 播放条没有同步`。

## 采用方案

1. 先把回归改为可诊断且自清理：保存失败 JSON、实际主/旁白/BGM 时间、`seeking/paused/readyState`、滑杆值和截图，失败也保留证据。
2. 使用物理鼠标拖动主滑杆，覆盖播放中第一次 seek、暂停、暂停态第二次 seek、恢复播放和刷新后的再次 seek；fresh Chrome 不绕过自动播放策略。
3. 以旁白为唯一主时钟，BGM 为从时钟；每次 seek 提交后等待媒体 `seeked` 或时间进入容差，再恢复并核对误差。
4. 若诊断证明 BGM seek 在 `readyState` 尚未取得 metadata 时被跳过，则缓存目标并在 `loadedmetadata/canplay` 补交；若证明播放恢复后独立媒体发生漂移，则只在超过容差时校正，避免每帧反复 seek。
5. 保留可见 BGM 原生控件和既有音量同步，不引入第二状态表。

## 未采用方案及原因

- 用 `timeupdate` 驱动主画布或每 250ms 强行覆盖：官方资料明确提示粒度和跨浏览器时序不足。
- 每个动画帧都写 BGM `currentTime`：会持续触发 seek、造成音频卡顿并掩盖真正的时钟关系。
- 关闭 Chrome 自动播放策略：不能代表用户真实环境。
- 改用 Web Audio 全量解码：会失去现有可见原生播放器/流式加载边界，修改范围过大。
- 只放宽旧断言或只检查按钮文字：不能证明第一次/第二次 seek、暂停、恢复和刷新后的真实同步。
- 修改 MoneyPrinterTurbo：与本项无关且明确禁止。

## 研究结论

当前实现方向符合标准：旁白主时钟、rAF 画布、BGM 从时钟和显式 seek 提交都是正确基线；但修改前真实浏览器回归已证明 seek 链仍失败，现有证据不足以区分异步 seek、metadata 时机或播放恢复漂移。应先增强真实回归保存精确状态，再据该证据做最小业务修复，禁止用更宽松的静态断言掩盖失败。
