# R2-01.04 修改前全网研究：TTS BGM 可见播放器加载与任务切换

## 检索记录

- 检索时间：2026-08-05 19:08–19:14（Asia/Shanghai）。
- 关键词：`WHATWG HTMLMediaElement currentSrc load resource selection`、`HTMLMediaElement play promise`、`Chrome autoplay policy user gesture`、`MDN HTMLMediaElement load currentSrc`、`W3C accessible media player controls audio control`。
- 范围：优先 HTML Living Standard、Chrome 官方开发文档、Mozilla MDN 和 W3C/WAI；未采用博客、论坛或搜索摘要作为结论依据。

## 一手来源与适用性

### 1. WHATWG HTML Living Standard：媒体资源选择

- 来源：[HTML Standard — Media elements](https://html.spec.whatwg.org/multipage/media.html)。
- 要点：设置或更改媒体元素 `src` 会启动媒体加载算法；`currentSrc` 由资源选择算法更新并表示当前实际媒体 URL；没有资源时应为空。
- 适用性：每次切换 BGM 必须把播放器 `src/currentSrc` 绑定到目标 BGM 的准确任务 ID；切到无 BGM 任务时必须清除旧 `src`，不能继续暴露上一任务的媒体。

### 2. MDN：动态换源后调用 `load()`

- 来源：[HTMLMediaElement.load()](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/load)。
- 要点：动态改变 `src` 后，`load()` 会重置媒体元素并重新执行资源选择；它也会中止旧媒体的进行中操作和旧 `play()` Promise。
- 适用性：现有 `showTtsBgmPreview()` 的“设置 `src` 后 `load()`”方向正确；清除旧任务时也应移除 `src` 并 `load()`，以终止旧播放和旧资源状态。

### 3. Chrome 官方：自动播放策略与真实用户操作

- 来源：[Chrome for Developers — Autoplay policy in Chrome](https://developer.chrome.com/blog/autoplay/)。
- 要点：有声 `play()` 在没有用户手势时可能以 `NotAllowedError` 拒绝；不应假设播放成功，应保留用户可操作控件并检查真实播放状态。
- 适用性：验收应使用 fresh Chrome，不关闭自动播放策略；先验证可见播放器和准确 `currentSrc`，再使用真实物理点击启动播放并确认 `currentTime` 推进。

### 4. W3C/WAI：媒体控件与音频控制

- 来源：[WAI — Making Audio and Video Media Accessible](https://www.w3.org/WAI/media/av/)、[WCAG 2.2 Understanding 1.4.2 Audio Control](https://www.w3.org/WAI/WCAG22/Understanding/audio-control)。
- 要点：媒体播放器应提供可访问控制；自动声音应可暂停、停止或独立控制，推荐由用户动作启动。
- 适用性：BGM 播放器必须保留原生 `controls`；测试不能通过禁用浏览器策略或隐藏控件来伪造播放成功。

## 本地调用链与修改前证据

- `showTtsBgmPreview()`：显示播放器、设置元信息、用目标 `audio_url` 更新 `src`、调用 `load()`，只在显式 `reveal/play` 时尝试播放。
- `clearTtsBgmPreview()`：隐藏播放器、移除 `src` 并调用 `load()`，是防止旧任务串音的正确清理入口。
- `showTtsAudioPreview()` / `showTtsAudioFile()`：有关联 BGM 时调用 `showTtsBgmPreview()`；无关联时当前只显示缺失面板，未先调用 `clearTtsBgmPreview()`，存在从有 BGM 任务切到无 BGM 任务后旧播放器和旧 `src` 残留风险。
- 修改前 `test-tts-bgm-player.mjs` 固定读取另一台机器任务 `93/94`，当前 B 数据库没有 BGM `94`，在第 20 行立即失败，不能到达播放器断言。
- 失败证据：`.data/repair-evidence/R2-01.04/20260805-190802/pre-fix/01-bgm-player.log`。
- 失败证据 SHA-256：`96FC931161026293A1D0F9F3FB4551344AED800D14519CF028E183A479987103`。
- 准确失败：`无法读取真实 BGM #94`；随后 Node 在异常收尾时报告 libuv handle closing 断言。

## 采用方案

1. 把回归改成自包含安全 WAV fixture，通过正常本地 API 创建两组已确认精确父子 BGM 关系和一条显式无 BGM 旁白。
2. fresh headless Chrome 中验证播放器 30 秒内可见、原生 controls 存在、`currentSrc` 指向准确 BGM ID、媒体时长与真实文件一致。
3. 不关闭 Chrome 自动播放策略；通过物理点击控件证明 `currentTime>0.15`。
4. 依次切换 BGM A → BGM B → 无 BGM旁白，验证换源准确且无 BGM 时播放器隐藏、`src/currentSrc` 清空、旧音频不再播放；刷新后复验。
5. 在所有无关联分支统一先调用 `clearTtsBgmPreview()` 再显示缺失面板，复用现有状态所有者，不增加第二套播放器状态。

## 未采用方案及原因

- 继续使用任务 `93/94`：只在原机器本地 SQLite 存在，无法复验。
- 关闭 Chrome 自动播放策略：会掩盖真实用户环境。
- 只断言 `src` 字符串或调用过 `play()`：不能证明资源可解码、播放器可见或实际播放。
- 为每个任务创建独立 `<audio>`：扩大状态所有者并增加并发串音风险。
- 切任务时只暂停不清空 `src`：旧媒体仍显示为当前资源，刷新或后续播放可能串音。
- 使用 mock DOM 或假音频：绕过真实 API、浏览器媒体栈和任务关系。

## 研究结论

现有播放器加载主路径符合标准，但无 BGM 分支没有调用既有清理函数，存在真实跨任务残留风险。应以最小源码改动统一清理，并用自包含真实浏览器回归覆盖两次换源、物理播放、无 BGM 清空和刷新恢复。

## 实施期诊断与采用结果

- 首轮局部诊断确认：仅执行 `pause()`、移除 `src` 并 `load()` 后，Chromium 中播放器虽已隐藏且暂停，`currentSrc` 仍可保留上一 BGM URL；这不足以证明跨任务资源已完全解除。
- 因此采用同一状态所有者内的最小补强：清理时暂停并卸载旧元素，再以无 `src` 的克隆元素原位替换，变量继续指向唯一播放器；未增加第二播放器或第二状态表。
- 自包含回归随后通过 BGM A → BGM B → 无 BGM → 刷新 → BGM A → 无 BGM 的完整链路；两次物理点击均推进播放时间，换源 ID 准确，无 BGM 后 `src/currentSrc` 为空且旧媒体暂停。
