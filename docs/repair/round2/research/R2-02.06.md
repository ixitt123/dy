## 一手来源、结论与适用性

### 1. 当前公告 GHSA-rgw5-rvv9-x895 / CVE-2026-69152

- 来源：[GitHub Advisory Database](https://github.com/advisories/GHSA-rgw5-rvv9-x895)、[上游安全公告](https://github.com/juliangruber/brace-expansion/security/advisories/GHSA-rgw5-rvv9-x895)。
- 范围：`2.0.0 <= version < 2.1.4` 受影响，2.x 首个修复版为 `2.1.4`；High、CVSS 7.5，CWE-400/CWE-770。项目当前 2.1.3 明确受影响。
- 根因一：逗号 alternatives 各自得到独立 `maxLength` 额度，汇入 `values` 中间数组时没有累计结果数和字符数上限；最终 `combine()` 限制执行前已经可能耗尽内存。
- 根因二：`expandSequence()` 只看结果数量 `max`，不看字符总长 `maxLength`；超宽补零序列先执行大量无用字符串工作，再由 `combine()` 丢弃，造成长时间事件循环阻塞。
- 风险：官方 PoC 的约 25 KB 输入可导致不可捕获的 V8 OOM，约 400 KB 输入可阻塞两分钟；应用层 `try/catch` 不能挽救 OOM 进程。
- 修复：上游在构建中间数组时同步累计 `max`/`maxLength`，并把 `maxLength` 传入 sequence 生成过程；超限时截断，合法常规输出保持一致。

### 2. 上游 2.1.4 发布与补丁

- 来源：[v2.1.4 发布](https://github.com/juliangruber/brace-expansion/releases/tag/v2.1.4)、[v2.1.3...v2.1.4 对比](https://github.com/juliangruber/brace-expansion/compare/v2.1.3...v2.1.4)、[上游修复提交 `688a99e`](https://github.com/juliangruber/brace-expansion/commit/688a99e)。
- 结论：2.1.4 是 2.x 兼容线的最小修复版本；提交把累计限制回移到 `values` 与 sequence 的构建位置，并修正被丢弃的空 alternative 不应占用 `max` 的兼容细节。
- 对本项目适用：两个 minimatch 版本均接受当前 2.x 依赖线；根 override 精确升到 2.1.4 可让两条传递路径统一，避免升级 glob/minimatch/archiver 主版本扩大影响面。

### 3. 前置长度型公告 GHSA-mh99-v99m-4gvg / CVE-2026-14257

- 来源：[GitHub Advisory Database](https://github.com/advisories/GHSA-mh99-v99m-4gvg)、[2.x/兼容线补丁背景](https://github.com/juliangruber/brace-expansion/commit/cb4b9e4)。
- 结论：链式 `'{a,b}'.repeat(N)` 虽受 `max` 限制结果数，却可让每个结果无限变长并使中间数组导致 OOM；2.x 的 2.1.3 加入默认 `max=100000` 与 `maxLength=4000000`，但当前公告证明其对 alternatives/sequence 的覆盖不完整。
- 对本项目适用：不能因为当前版本已是 2.1.3 或只看到 `maxLength` 常量就判定安全；必须升级 2.1.4 并动态覆盖绕过路径。

### 4. 零步长公告 GHSA-f886-m6hf-6m8v / CVE-2026-33750

- 来源：[GitHub Advisory Database](https://github.com/advisories/GHSA-f886-m6hf-6m8v)。
- 结论：`{1..2..0}` 的步长绝对值仍为 0，会让旧版 sequence 循环不前进；2.x 从 2.0.3 起把零步长规范成 1。2.1.4 已包含该修复。
- 对本项目适用：新回归同时覆盖零步长，以防未来 override 或锁文件回退时只关注新公告。

### 5. 本项目调用链与不可信输入边界

- 本地来源：`package.json`、`pnpm-lock.yaml`、`pnpm why brace-expansion --depth 10`、`server/kinetic-text/kinetic-text-service.js`。
- 项目没有直接导入 `brace-expansion`、`minimatch` 或 `glob`；唯一 archiver 业务调用为 `archive.directory(sourceDir, false)`，第二个参数关闭目标根目录包裹，并未调用 `archive.glob()`，也没有把用户文本当 glob pattern。
- 对验收适用：除依赖升级外，应动态创建带 `{a,b}`、`*`、`[]` 字符的真实文件名并经 `archive.directory` 打包，证明这些不可信文件名按字面值进入 ZIP，而不是作为 brace/glob 模式展开。

## 采用方案

1. 将根 `pnpm.overrides.brace-expansion` 从 2.1.3 精确升级为 2.1.4，刷新锁文件并冻结安装；用 `pnpm why` 证明两条 minimatch 路径只解析到 2.1.4。
2. 新增 `test-brace-expansion-dos.mjs` 并接入 `check:gate`，动态加载真实活动依赖，验证版本、锁文件和官方 registry 审计切片。
3. 所有资源型 PoC 只在独立 Node 子进程中运行，设置小堆上限与硬超时；父进程保存退出码、用时、输出规模和最大结果长度，禁止在主测试/服务进程直接运行 OOM 样例。
4. 受控覆盖三类风险：链式长度、逗号 alternatives 中间数组、宽补零 sequence；另验证零步长结束。PoC 必须按时退出且输出受 `max`/`maxLength` 约束。
5. 用真实 archiver 生成临时 ZIP，确认含 brace/glob 元字符的文件名被字面归档；测试结束精确清理临时目录，不接触用户下载、项目或素材。

## 未采用方案及原因

- 不在 2.1.3 上直接运行官方 OOM PoC：官方明确说明约 25 KB 输入可不可捕获地杀死进程；即使放在 `try/catch` 也不安全。修复前失败由版本/锁文件与官方审计稳定暴露，资源 PoC 只在升级后以隔离子进程执行。
- 不只把 `maxLength` 设小：公告明确说明受影响版本按 alternative 分配独立额度，单纯减小该值仍可绕过。
- 不升级到 5.0.9 或同时升级 archiver/glob/minimatch：2.1.4 是官方 2.x 修复线，可最小化兼容变化；跨主版本留给独立依赖升级评估。
- 不新增业务层 brace 正则或复制上游展开器：项目没有直接展开不可信 pattern，重复解析器会增加错误与维护面；供应链修复加真实归档边界回归更直接。
- 不修改 MoneyPrinterTurbo、全局 Node/pnpm、设置、SQLite、密钥或本地素材：均不属于本项依赖与输入边界。
