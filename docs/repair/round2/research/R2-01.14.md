## 一手来源与适用性

1. [Node.js v24 Process 文档](https://nodejs.org/download/release/v24.11.0/docs/api/process.html#processkillpid-signal)
   - 官方说明 `process.kill(pid, 0)` 可跨平台检查 PID 是否存在，但它只证明“有这个进程”，不能证明该 PID 就是当前项目的服务实例。
   - 适用性：PID 存活必须检查，但不能单独作为复用依据；还需由目标 HTTP 实例返回项目身份，并校验项目根、入口、commit 和实例标识。
2. [Node.js File system 文档](https://nodejs.org/download/release/latest-v24.x/docs/api/fs.html#fspromisesrealpathpath-options)
   - `realpath` 用于取得规范化绝对路径，Windows 路径还需进行大小写不敏感和分隔符统一比较。
   - 适用性：启动器不能直接比较未经规范化的字符串路径，应比较真实项目根和真实 `ui-server.mjs` 路径。
3. [Playwright 官方 webServer 文档](https://playwright.dev/docs/test-webserver)
   - `reuseExistingServer` 的通用就绪判据是指定 URL 可接受连接并返回一组 HTTP 状态；该机制用于已知测试配置，不提供应用项目身份校验。
   - 适用性：本项目的 `ui-server.url` 可被陈旧文件或另一份工作树污染，因此不能照搬“HTTP 可响应就复用”，必须增加产品级身份握手。
4. [OpenAI Codex 上游 responses-api-proxy](https://github.com/openai/codex/blob/main/codex-rs/responses-api-proxy/README.md)
   - 上游在服务真正监听后写入单行 server-info JSON，至少把 `port` 与 `pid` 绑定，供调用者识别目标进程。
   - 适用性：本项目继续保留兼容的 URL 文件，但真实复用决策应从服务实例读取带 PID 的结构化身份，不应仅信任 URL 文本。
5. [Jupyter Notebook 上游 server-info 讨论](https://github.com/jupyter/notebook/issues/2375)
   - 上游的 `list --json` 从 server info file 输出正在运行服务的结构化信息，而不是只保存一个裸 URL。
   - 适用性：支持把运行实例的 URL、PID、项目根等字段视为一个整体；本项目采用 HTTP 身份端点，避免把额外敏感字段写入仓库根文件。

## 本仓库诊断

- `launch-ui.mjs` 当前读取 `ui-server.url` 后只对根页面执行 `fetch(url)`，任何返回成功状态的本地 HTTP 服务都会被记为 `reuse-existing`。
- `ui-server.mjs` 已计算 `runtimeVersion`，也已有 PID 锁和 Windows 入口命令行核验，但 `/api/status` 受浏览器会话 Cookie 保护，启动器不能把它作为无 Cookie 的身份探针。
- URL 文件可能属于旧进程、另一份项目工作树或同端口上的无关服务；“URL 可访问”不等于“正确项目、正确代码和正确 PID”。
- 现状没有 `test-launcher-project-identity.mjs`，因此任务卡规定的修复前回归目前以 `MODULE_NOT_FOUND`、非零退出稳定失败。

## 采用方案

1. 在 `ui-server.mjs` 提供只含非敏感运行元数据的本地身份端点；继续先执行 Host/本机边界校验，但该端点不依赖浏览器会话 Cookie。
2. 身份至少包含固定服务标识、规范项目根、规范入口、随机实例 ID、PID、完整 commit、入口启动时 mtime、启动时间和 ready 状态。
3. `launch-ui.mjs` 仅接受本机 HTTP URL；复用前校验身份端点、项目根、入口、commit、PID 存活、实例 ID、ready 和源文件 mtime。任一字段不符即删除当前项目的陈旧 URL 文件并启动当前项目实例。
4. `ui-server.mjs` 的并发复用路径也使用同样的身份判据，避免 PID 锁存在时仍打开错误 URL。
5. 新增动态回归覆盖：错误项目根、错误 commit、错误 PID、陈旧/不可达 URL 均不得复用；正确身份必须复用；错误 URL 被清理后应启动当前项目实例并留下真实 PID、URL 和身份响应证据。

## 未采用方案及原因

- 仅检查 HTTP 200：无法区分错误项目或同端口无关服务，正是本项根因。
- 仅检查 PID 存活：PID 会复用，且只证明某进程存在；Node 官方语义不包含项目身份。
- 只比较 URL 文件时间：mtime 不能证明服务身份，复制、恢复或进程崩溃后仍可能陈旧。
- 把 token、Cookie 或设置写进身份文件/端点：身份核验不需要秘密，且违反本项目本地敏感数据边界。
- 自动终止响应错误的进程：无法证明该进程归本项目所有；本项只清理当前工作树的陈旧 URL 并启动正确实例，不杀无关服务。
- 改为 JSON URL 文件且立即破坏旧格式：会破坏既有启动与人工读取流程；本轮保留裸 URL 文件兼容性，可信身份来自实时端点。
